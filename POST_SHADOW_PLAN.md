**Version:** 2.5 · **Date:** 2 November 2026 · **Branch:** `post-shadow-fixes` (from `pi-snapshot-0.5.36`)  
**Covers:** the 25 open GitHub issues (#1–#3, #5, #6, #8–#26, #29), raised by the 1 November shadow test (`TESTING_REPORT_2026-11-01.md`) and an external code review.  
**Relationship to `DEVELOPMENT_PLAN.md`:** this plan details the fixes that Stage B (protect and validate) and the go-live conditions of Stages C and D depend on. ## Revised approach (owner, 1–2 November 2026)

Two decisions shape every package. The other documents have been brought into line with them: `SOFTWARE_SPECIFICATION.md` (1.8), `REQUIREMENTS_AMENDMENTS.md`, `DEVELOPMENT_PLAN.md`, `OPERATIONS.md`, `CODE_REUSE.md`, `deployment/README.md` and `README.md`.

1. **Control is built as explicit state machines using `transitions`.** The state table is the decision table of the owner's functional specification v1.3 (sections 5 to 11), which the owner confirmed is correct. Each machine is a declared table (states, triggers, guards) built through one shared helper, so the tests, the change log and the generated diagrams all read the same table. `transitions` is the controller's one approved third-party library (owner approval, 2 November). Checked on 2 November: version 0.9.3, MIT licence, Python 3.11 to 3.13, needs only `six` (already pinned in `requirements.lock`). With `auto_transitions=False` there are no `to_<state>` shortcuts. Checked on 2 November against 0.9.3: an event that is declared but not allowed from the current state raises `MachineError`, while an event name that was never declared raises `AttributeError`, so the helper checks the name against its table first and handles the two cases separately, without changing state; guards driven by a simulated clock handle dwell timers.
2. **High-rate telemetry goes to a fixed-size data logger built on Whisper.** Per-second readings, one-minute observations and charger coverage move out of SQLite into Whisper files (issue #16): one file per metric, 1 second for 2 days, 1 minute for 90 days, 30 minutes for 10 years, written only by the collector in batches, never touched by the controller. SQLite keeps settings, plans, charger sessions, half-hour and daily records, events and everything transactional. Checked on 2 November with Whisper 1.1.10 (Apache 2.0, needs only `six`): 5.73 MB per file and unchanged after writes; a gap stays empty at every resolution; a mostly missing minute stays empty with `xFilesFactor` 0.5; and when the rest of a minute arrives in a later batch the one-minute average corrects itself (1 s at 1 kW then 59 s at 3 kW gives 2.97 kW whatever the flush point), which is the fault in #24. A minute built from 30 valid seconds gives the same mean as one built from all 60, so each metric whose coverage matters also keeps a count of its valid seconds (contract TC). The PyPI name `whisper` is the Graphite library, not OpenAI's `openai-whisper`.

## 2. Working rules

1. **Reproduce first.** Each package starts with the issue's "Test to add", shown failing on the current code. #19–#25 were confirmed by reading the code in another session, not by running it. If the test already passes, stop and report instead of changing code.
2. **One branch per package** off `post-shadow-fixes` (for example `fix/wp1-midnight-plan`), merged back by pull request. A pull request says `Refs #n`. An issue is closed only when its evidence is recorded (the `DEVELOPMENT_PLAN.md` rule: *Done* needs evidence).
3. **Status words** (as in `DEVELOPMENT_PLAN.md`): Open → Built (merged, suite green) → Running in shadow (deployed) → Done (evidence recorded).
4. **Evidence** is a dated testing report in the format of `TESTING_REPORT_2026-11-01.md`, plus an `OPERATIONS.md` release note and a status row in `DEVELOPMENT_PLAN.md`.
5. **The shadow series breaks at every behaviour-changing release.** The house has been empty since 1 November, and the planner and controller change under the trial. Pool Anker-AI comparison results only within one release's soak, and record each release's deploy time.
6. **Dependencies.** The controller's one approved third-party library is `transitions` (0.9.3); the collector's is `whisper` (1.1.10). The controller never imports `whisper`, and telemetry writes never block the one-second loop. Both need only `six`, already pinned. Each is pinned in `pyproject.toml` and `requirements.lock`, because `install-pi-shadow.sh` installs from the lock and runs the suite on the Pi. Test-only Hypothesis (6.170.14 with `sortedcontainers` 2.4.0) goes in the `test` extra and in the lock for the same reason. The first release that adds a dependency builds a fresh environment (the lightweight code update cannot add one).
7. **Machines are data.** Every controller state machine is a declared table built through the WP11 helper; nothing outside the helper calls `transitions` directly.
8. **Nothing here sends a command to the battery.** Anything that needs the live transport is split out and left to Stage C (section 6).
9. **One dependency list.** The 'After' columns in section 4 are the only dependency list. The lanes and releases in section 5 are derived from them, and `scripts/check-docs.py` fails when a release ships a package before something it waits for, or a package is missing from a lane or a release. Run it before every commit to this branch.
10. **Shared contracts.** Packages and issues refer to the contracts in section 11 (LC, TC and RC) by number and do not restate them. To change a contract, change section 11 first.
11. **Commission what you deploy; going live is configuration only (owner, 3 November).** Data is kept in one place only (Whisper for minute detail, SQLite for settings, events and records), and the code commissioned in shadow and logged mode is the code that goes live. Going live changes only root-owned files (control mode, commissioning record, write-switch), never code. A code change after commissioning means commissioning is repeated for the changed part (RC4).
12. **Samples go to the telemetry files; records go to SQLite (owner, 5 November).** Anything that is a number sampled over time (readings, the car's power, any series we want to analyse later) is stored only in the fixed-size telemetry files, at the resolution the files give (1 s for 2 days, 1 min for 90 days, 30 min for 10 years). Documents (plans, forecasts, raw responses), decisions, settings and per-event records (a car-charging session and its energy, a daily record) stay in SQLite, each with a retention rule. The charger's per-minute sample rows and the collector's reading rows are no longer written to SQLite.

## 11. Contracts shared by several packages

### LC. Controller lifecycle: release, exit and the fault latch (WP10, WP14, WP24; D9, D17, D18)

**LC1. One release rule.** Software cannot hand control back to the Anker app: the app's own settings, including its third-party-control switch, are changed by hand (owner, 2 November). What the controller can do is release the battery by writing the **default mode** to register 10064, after set-point 0 W. The default mode is the owner's **Dynamic Tariff**, which this device reports as value 6 (the vendor's table calls 6 'Smart'); it is kept in one place so it can change. The controller releases when it stops or restarts (LC2), when data other than the charger is invalid or stale (D9), and when the owner presses the button now called 'Hand control to the Anker app', which means 'release to the default mode' and says so. The device lists Smart (value 6) among the modes it offers (its mode mask reads 47, first readings of 29 October: H10), but whether a write of 6 takes effect and the AI then behaves as the app's Dynamic Tariff does is unproven: the first commissioning test of the mode change (T5, extended to 3 to 6) checks it, and until it passes, or if the read-back differs, the controller writes mode 0 (self-consumption) instead and raises an alert. While the controller is stopped or has released, the Anker's own mode decides, as it did before the controller existed; the controller's extra rules (never discharge in a cheap period, the car block) apply only while it runs. The evening DISCHARGE keeps writing mode 0, as v1.3 and the 30 October decision say (confirmed by the owner on 3 November, D17 (a)). v1.3 differs in two places: 11.1 holds at 0 W on invalid data, and 11.1 and 11.6 write mode 0 on a release.

**LC2. Exit order.** On SIGTERM, SIGINT, an unhandled exception, a planned restart or a deployment, in this order: (1) write set-point 0 W, so a charge request never outlives the garage regulation; (2) write the default mode (LC1); (3) log the exit. With HANDS_OFF latched nothing is written. If Modbus is unavailable nothing can be written and an alert is raised. Each write is tried once with a short timeout, and the unit's `TimeoutStopSec` (15 s today) must cover them (a unit-file test). The new instance takes over from the default mode when it starts (LC3). A killed or power-cut process runs no handler and the unit keeps its last set-point (v1.3 11.3, test T6); software cannot cover that case.

**LC3. Startup** needs no memory of the previous instance except the latch below. It reads the registers, runs the 11.5 checks, waits for VALID and evaluates the decision table, whatever mode the previous instance left.

**LC4. The HANDS_OFF latch.** HANDS_OFF must survive a restart. Otherwise a restart discards it, fresh readings become valid and automatic commands resume without anyone resetting it (the rules said "only by manual reset" but nothing stored it).
- *Record:* `control-latch.json` in `/var/lib/solarbank-cost-optimiser` (the controller already writes `control-commands.jsonl` there, and its unit allows writes to that folder): schema version, cause, time entered, release id.
- *Writer:* only the controller, atomically (write a temporary file in the same folder, flush it to disk, rename it, flush the folder). The dashboard shows it through the controller's status file.
- *Reader:* the controller reads it first at startup, before any device connection. Present, unreadable, corrupt or of an unknown version all mean latched (the last three with cause `latch_unreadable`). A latched controller writes nothing.
- *Reset:* the owner presses a reset button; the web side saves a request (id and time) in the settings, and the planner carries it to the controller with the plan, as it carries pause and override today. The controller honours a request that is newer than the latch and not used before, only after the 11.5 checks pass and VALID holds; it then deletes the latch and logs HANDS_OFF to STARTUP with the request id.
- *If the write fails:* HANDS_OFF still holds in memory; the controller also tries `/run/solarbank-cost-optimiser/control-latch.json` (kept across service restarts by `RuntimeDirectoryPreserve=yes`, lost at a reboot), retries the durable write every 10 s, alerts, and does not exit.
- *Alternative considered:* the controller asks the web side to persist the fault. Rejected because the web side may be down at the moment of the fault, and two copies of one fact can disagree.

This is the one exception to "the controller keeps no persisted state" (Phase 4b); it is decision D18.

**LC5. Acceptance tests (WP14, with WP10's properties).**
- HANDS_OFF, then a restart, then fresh valid readings: still no writes; then a reset request: the checks run, the latch is removed, normal operation resumes. Also with a corrupt latch, a latch that cannot be written, and a reset request older than the latch.
- Exit at each action (CHARGE, ZERO_OUTPUT, DISCHARGE, HOLD) as a planned restart, a deployment and an unhandled exception: set-point 0 W is written first, then the default mode, and a charge set-point is never left running; when the device refuses the default mode, mode 0 is written and an alert is raised.
- Invalid or stale data other than the charger releases to the default mode, and normal operation returns once VALID has held for 30 s (D9). Hypothesis: after any exit or release the unit is never left in mode 3 with a non-zero set-point.

### TC. Telemetry and records: what must survive the move to Whisper (WP15, WP19, WP23a to WP23c)

**TC1. What is stored.** One value file per metric (WP23a). Whisper keeps only the aggregate of an interval, so a minute built from 30 valid seconds and one built from 60 have the same mean (checked on 2 November: both 1,000 W; 29 valid seconds leaves the mean empty). So every metric with a coverage consumer also has a **count file** (`sum`, `xFilesFactor` 0): a 1 is written at every second a valid value was written. Its one-minute point is the number of valid seconds (0 to 60) and its 30-minute point the number out of 1,800 (checked: 1,200 of 1,800 after 20 full minutes). The metrics are the five of the daily record (SoC, battery, grid, PV and household power) and the charger power; SoC also has a `max` file for the calibration check. An invalid or missing reading writes nothing to either file, so "quality OK" means "a value exists". **A gap of up to 5 s between two valid readings counts as covered, holding the earlier value** (the rule the old minute recorder used; decided after review and confirmed by the owner, 3 November), so a device that refreshes every other second still covers the minute. About 22 files, roughly 125 MB, fixed.

**TC2. `minute_source`.** One interface, over SQLite now and Whisper after WP23b, returning per minute the mean, the covered seconds (0 to 60), `complete` (60) and, for household power, the demand mode and revision. The demand mode and revision come from the settings history (`setting_at`), the same lookup that tags observations today; a minute in which the selection or its revision changes is `broken` and never complete. The rules that use it stay as they are: the daily record counts a minute with at least `MIN_OK_SAMPLES` (30) covered seconds; the Normal-day choice needs a complete, unbroken Normal minute, no duplicates and a non-negative value; calibration reads the SoC maximum; charger history takes its covered seconds from the charger's count series. Every reader goes through it: the planner's demand history, the dashboard charts, calibration, validation, the daily and half-hour records, and the charger history (`car_history`, `car_power_minutes`).

**TC3. Tests that need old data.** Every reader is also tested on history older than two days, when the one-second archive no longer holds it: the same Normal-day eligibility, the same daily and half-hour records and the same charger-history coverage as on fresh data. A comparison on fresh data alone cannot find this fault.

**TC4. One finalisation check.** A day's minute detail in SQLite (until WP23c) is removed only from a FINAL record, and a sealed record counts. Routine retention (WP15) and the emergency purge (WP19) call the same function. In an emergency a day that is not FINAL is first finalised from what it holds and sealed with its covered minutes; if that cannot be written, its minute rows stay and the other detail (plan and forecast archives, events) goes first. The guard never stops a service to make room.

**TC5. Late data and the correction window.** Whisper merges a late point into the coarser averages only while the point is inside the one-second archive (2 days from now). Checked on 2 November: a minute completed in a later batch, 1.5 days late, gives the right mean and count; the same minute written 3 days late stores only its last value (3,000 W instead of 2,000 W) and a count of 1, not 60. So: (1) the collector never writes a point older than 2 days less a one-hour margin; it drops it, counts it and records an event, and only a repair command writes older data, with complete minute values and counts together; (2) a day can be corrected automatically until 22 hours after it ends (its first second leaves the one-second archive 24 hours after the day ends, and the collector's one-hour margin and one hour of slack come off that); (3) a day is FINAL once its record was calculated after the collector's flush watermark passed the end of the day (plus the settle time); (4) if it is not FINAL 12 hours after the day ends an alert is raised, and at 22 hours the day is sealed: FINAL, with its covered minutes and gaps recorded, so unresolved coverage is reported and not hidden; (5) a later correction is the explicit repair command, which recalculates from the one-minute archive (kept 90 days) and says so in the record.

**TC6. Prices belong to the day.** A recalculation prices each interval from the tariff and cheap window in force at that time, taken from the settings history (`setting_versions`: validity dates and revisions), and records the revisions used as the price source. A recalculation caused by late readings reuses the day's recorded price context; re-pricing a day is a separate, explicit command. Reproduced on 2 November with the branch code: a 31 October profile priced at 27p became unpriced after a tariff valid from 1 November was saved, although the old revision was still in the history.

### RC. Rollback, deployment and the go-live gates (WP2, WP23b, WP23c, section 6; D19)

**RC1. Rollback after the telemetry switch (single store).** `switch-release.sh <previous release id>` backs up the database and activates another release; it does not rebuild deleted history. WP23b stops the SQLite minute and coverage writes in the same release in which the readers move, so an older release would read minute history that ends at the switch. So: (1) the old rows are **not deleted** and the backfill is repeatable; (2) the WP23b release writes a marker naming itself as the oldest compatible release and `switch-release.sh` refuses an older one unless forced; (3) the pre-switch backup (taken by the deploy script) is the way back past the marker, and restoring it drops settings and readings saved since, so it is a last resort; (4) the old rows are dropped only by an explicit command (WP23c), after a verified backup and 90 days.

**RC4. Commission what you deploy.** The sending transport is part of the shadow release, installed but unable to send: it needs three root-owned, default-off conditions together: the control-mode file says `live`, a commissioning record lists the mandatory tests as passed for this release, and the write-switch file allows the class (`mode`, `setpoint`). The files live in `/etc/solarbank-cost-optimiser`, a root-owned folder (not the service's data folder), and the controller believes one only when root owns it and nobody else can write it. A zero set-point is protective and is allowed when `mode` is. The switch is read before every register write.
